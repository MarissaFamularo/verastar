# Beta NPI match

Deployed and smoke-tested on 2026-10-12. The following describes the release requirements. Requires deploying both `match-npi` and the updated `redeem-invite` Edge Functions together with the frontend. Release order: deploy `match-npi` first, then the frontend NPI flow, then updated `redeem-invite` in the same beta cutover; do not open beta admission until all three are live and verified. Deploying the redemption guard first temporarily blocks unmatched older clients. No schema migration is required. No paid model calls are involved.

NPI is required only for beta access through an invitation. Enter a beta access code first; a valid, usable code then asks for first name, last name and NPI. Ordinary setup and BYOK do not require NPI. The success text is **NPI matched**. Preview explicitly says no check is performed; sample access remains available. Unconfigured local clones retain their local setup path.

The authenticated function validates the ten-digit NPI checksum, looks up the exact number using CMS NPPES API v2.1, requires an active individual record (`NPI-1`, `basic.status === 'A'`), and compares the registry first and legal last name. Case, diacritics, spaces, apostrophes, periods and hyphens do not affect comparison. Both names must match; no nickname/fuzzy/alternate-name guessing. A mismatch asks the user to enter the registry name. This is friction, not physician credentialing, identity proof, or current-license verification; there is no taxonomy filter or review queue.

Match requests are limited to ten per account per hour using existing events, fail closed if rate-limit reads/writes fail, and have an eight-second registry timeout. Only successful persisted matches return success. Registry outages are retryable; no failure is treated as a match. No name/NPI is logged in event payloads. The receipt contains only NPI, registry first/last names, timestamp and version in server-owned `app_metadata.npi_match`, preserving other metadata. Receipt is bound to the authenticated account. It is not unique across accounts and does not prove identity.

For an account without a receipt, invitation redemption first reads the exact code non-consumingly through the service role. Invalid, revoked, expired and exhausted codes return their own status without asking for NPI. Existing account already/revoked precedence matches the SQL RPC. A usable beta code returns npi_required; no use is reserved or consumed. After NPI matching, final redemption checks the server-owned receipt and calls the existing atomic RPC, which rechecks code/account state, enrollment pause and capacity before consuming the code. Existing spending-contract guard and five/hour invite limit remain. The Settings invite path also offers NPI entry. Existing sponsored accounts and onboarded libraries remain accessible without retroactive gate or modification; scheduled digests/billing are unchanged. Existing accounts that seek a new invitation must match first. Email account creation itself precedes the NPI check. This is beta-invitation enforcement, not a general setup requirement or a new RLS restriction on every data operation or BYOK backend call.

Unit tests use fabricated fixtures and mocked network/auth. Hosted smoke tests verified a public registry match, name mismatch, authenticated receipt persistence, invalid-code refusal, valid-code NPI requirement, and final enrollment using a separate zero-budget QA invitation. The QA sponsorship was disabled and its invitation revoked afterward; the real beta code remained unused. Live status `A` was confirmed. Registry outage behavior is covered by mocked tests. Fresh email delivery and a new paid interview/digest were not exercised in this release. Deploying frontend alone without its functions would fail closed at NPI matching.
